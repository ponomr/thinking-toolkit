# 🧠 Thinking Toolkit

[English](README.md) · **Русский** · [中文](README.zh.md)

**30 проверенных практикой моделей мышления в одном переносимом скилле для любого AI-агента.**

Thinking Toolkit учит агента *думать о том, как думать*: получив реальный
запутанный запрос — принять решение, диагностировать проблему, разобраться в
системе, выстроить сообщение — он выбирает минимально достаточный набор
структурных моделей мышления, добросовестно применяет их шаг за шагом и
возвращает конкретный артефакт: взвешенную матрицу, карту причинных связей,
таблицу premortem, обратный план, черновик сообщения.

Это чистый Markdown без единой runtime-зависимости. Если ваш агент умеет
читать файлы — он умеет пользоваться этим скиллом.

## Зачем

Предоставленный сам себе, LLM-агент рассуждает убедительной прозой и
перескакивает через шаги. Между тем инженерия, стратегия, разведывательный
анализ и организационное обучение десятилетиями превращали ситуации, с
которыми агенты сталкиваются ежедневно, — сравнить варианты, найти корневые
причины, оценить без данных, испытать план на прочность — в именованные,
проверенные процедуры. Этот скилл превращает их в инструкции, которые агент
выполняет шаг за шагом, вместе с ошибками, которые практики задокументировали
по дороге.

Дизайн держится на трёх решениях:

1. **Выбор.** Знать, что такое матрица решений, легко; дорогая ошибка —
   схватиться за неё в неподходящий момент. Каталог кодирует сигналы выбора,
   правила контраста («Five Whys — для одной причинной цепочки, Ishikawa —
   для ширины, Connection Circles — для обратных связей») и анти-паттерны для
   каждой модели.
2. **Процедура.** Каждая модель — полная операционная карточка: входы,
   пронумерованные шаги, направляющие вопросы, формат результата, разобранный
   пример и задокументированные ошибки практиков. Агент следует карточке
   вместо импровизации вокруг названия.
3. **Честность.** Базовый контракт отделяет наблюдаемые факты от допущений,
   помечает неизвестное вместо выдумывания доказательств, проверяет
   чувствительность значимых результатов и завершает каждый артефакт
   действием и триггером пересмотра.

## Как это работает

Если модель названа явно, агент загружает её карточку и следует ей. Если
запрос открытый — агент определяет задачу (решить, диагностировать, оценить,
картировать, разрешить конфликт, донести мысль), проходит по сигналам выбора и
правилам контраста в каталоге и выбирает одну основную модель максимум с двумя
дополняющими. Затем он очерчивает ситуацию — ставки, обратимость,
доказательства, — проходит процедуру карточки на быстрой, стандартной или
глубокой глубине, проверяет результат на скрытые допущения и чувствительность
и завершает артефактом, действием и триггером пересмотра.

Скилл использует **прогрессивное раскрытие**, чтобы экономить контекст: агент
сначала читает только `SKILL.md` (~180 строк), обращается к каталогу-роутеру
при неочевидном выборе и загружает *только* реально нужные карточки. Тридцать
моделей ничего не стоят, пока не используются.

## Каталог

### Принятие решений — 12 моделей

| Модель | Когда применять |
|---|---|
| Six Thinking Hats | Выбору нужны сбалансированные перспективы вместо спора |
| Eisenhower Matrix | Задачи различаются срочностью и важностью |
| Second-Order Thinking | Немедленная выгода может скрывать поздние эффекты |
| Decision Matrix | Несколько вариантов нужно сравнить по взвешенным критериям |
| Impact-Effort Matrix | Бэклогу нужна грубая портфельная приоритизация |
| Ladder of Inference | Вывод мог обогнать свои доказательства |
| Hard Choice Model | Непонятно, сколько усилий заслуживает решение |
| OODA Loop | Условия меняются прямо по ходу действия |
| Cynefin Framework | Ответ должен соответствовать причинной природе ситуации |
| Confidence → Speed vs. Quality | Продуктовая работа требует размена скорости на качество |
| Pareto Analysis | Немногие источники могут давать большую часть измеримого эффекта |
| Backcasting | Далёкой цели нужен путь от конечной точки к сегодняшнему дню |

### Решение проблем — 11 моделей

| Модель | Когда применять |
|---|---|
| Ishikawa Diagram | У определённого эффекта много возможных причин |
| Five Whys | Один инцидент нужно проследить по цепочке до процессного исправления |
| Abstraction Laddering | Формулировка проблемы может быть слишком узкой или размытой |
| Conflict Resolution Diagram | Противоположные требования кажутся взаимоисключающими |
| Zwicky Box | Решение можно собрать из независимых измерений |
| Productive Thinking Model | Определённой проблеме нужен полный творческий процесс |
| Inversion | Сценарии провала подсказывают путь к успеху |
| Red Teaming | Уверенному плану нужен независимый состязательный вызов |
| Issue Trees | Большую проблему нужно разложить без пересечений |
| First Principles | Конвенции и аналогии ограничивают качество решения |
| Fermi Estimation | Величину нужно оценить без прямых данных |

### Системное мышление — 5 моделей

| Модель | Когда применять |
|---|---|
| Iceberg Model | Повторяющиеся события указывают на глубинные структуры и убеждения |
| Connection Circles | Нужно картировать переменные и обратные связи |
| Concept Map | Нужна ясность в понятиях и их смысловых отношениях |
| Balancing Feedback Loop | Система сопротивляется изменению или стремится к цели |
| Reinforcing Feedback Loop | Рост или спад подпитывают дальнейший рост или спад |

### Коммуникация — 2 модели

| Модель | Когда применять |
|---|---|
| Situation-Behavior-Impact | Обратная связь должна быть конкретной и безоценочной |
| Minto Pyramid | Занятой аудитории нужен вывод в первую очередь |

Помимо одиночных моделей, каталог содержит **рецепты комбинаций** —
проверенные последовательности вроде *Consequential choice* (Hard Choice
Model → Decision Matrix → Red Teaming) или *Root-cause investigation*
(Pareto → Iceberg → Ishikawa → Five Whys → OODA) — плюс ограждения от
классической ошибки: громоздить модели ради видимости основательности.

## Анализ логики (`/logic`)

30 карточек помогают *выбрать, как думать*. `/logic` делает обратное: он
*проверяет уже готовое рассуждение* — тезис, аргумент, черновик — и выдаёт
вердикт о его логической состоятельности.

Модуль поставляет **дисциплину, а не учебник**. Модель и так знает, что такое
modus tollens; `/logic` добавляет фиксированную процедуру (реконструкция →
проверка формы → разделение формы и истинности → вердикт), единую таксономию
ошибок с устойчивыми английскими + латинскими названиями и повторяемый формат
вердикта. Три режима, по ключевым словам, на любом языке:

- **review** (по умолчанию) — диагноз и вердикт, без переписывания.
- **fix** — починить рассуждение минимальным вмешательством, сохранив голос.
- **solve** — учебная задача (проверить силлогизм, построить таблицу истинности,
  применить метод Милля, восстановить энтимему).

> *«Проверь логику: мы выкатили редизайн, и регистрации выросли — значит,
> редизайн сработал».*
> → **1 критичная ошибка.** *Post hoc ergo propter hoc* — рекламная кампания той
> же недели не исключена как причина. Формально невалидно; посылка может быть и
> верной, но аргумент её не доказывает.

Модуль опирается на четыре сжатых файла: [overview](logic/overview.md) (процедура
+ формат вердикта), [таксономия ошибок](logic/fallacies.md),
[формальная валидность](logic/formal-validity.md) (силлогизм + пропозициональная)
и [индукция](logic/induction.md) (методы Милля, аналогия, гипотеза).

## Установка

Скилл следует конвенции [Agent Skills](https://simonwillison.net/2025/Dec/12/openai-skills/)
(`SKILL.md` + файлы ресурсов), которую поддерживают Claude Code, OpenAI Codex
CLI, OpenClaw и другие среды со SKILL.md. Установка — копирование папки.

### Быстрая установка

```bash
git clone --depth 1 https://github.com/ponomr/thinking-toolkit.git && thinking-toolkit/install.sh
```

Ставит во все обнаруженные на машине агенты, печатает каждый путь и не
перезаписывает существующую установку без подтверждения.

Опции:

- Конкретный хост: `./install.sh claude`, `codex`, `openclaw` или свой путь.
- `--symlink` — симлинк вместо копии, тогда `git pull` в этом репо обновляет
  все установки разом.
- `--force` — перезаписать существующую установку без вопроса.

### Ручная установка

| Агент | Личный каталог скиллов | Проектный |
|---|---|---|
| Claude Code | `~/.claude/skills/thinking-toolkit/` | `.claude/skills/thinking-toolkit/` |
| OpenAI Codex CLI | `~/.codex/skills/thinking-toolkit/` | `.codex/skills/thinking-toolkit/` |
| OpenClaw | `~/.openclaw/skills/thinking-toolkit/` | `.openclaw/skills/thinking-toolkit/` |
| Любой другой | Где ваша среда находит `SKILL.md` | — |

Скопируйте `SKILL.md`, `references/`, `logic/` и (опционально) `agents/` в
каталог. Папки `scripts/` и `tests/` — это инструменты репозитория, а не
пейлоад скилла; их копировать не нужно. Больше ничего не требуется: ни
API-ключей, ни сети, ни исполнения кода.

Для self-hosted-шлюзов и кастомных сред: добавьте `SKILL.md` в системный
контекст и сделайте `references/` читаемыми — скилл не предполагает ничего,
кроме чтения файлов.

## Использование

Попросите модель по имени:

> *«Прогони premortem по этому плану запуска.»*
> *«Сравни трёх вендоров взвешенной матрицей.»*
> *«Сделай backcasting от того, где рассылка должна быть через три года.»*

Или просто опишите ситуацию и доверьтесь роутингу:

> *«Тикеты в поддержку растут, не знаю, с чего начать.»*
> → Pareto Analysis для поиска «жизненно важного меньшинства», затем
> Five Whys по верхней категории.

> *«Мы всё спорим, переписывать ли биллинг.»*
> → Six Thinking Hats для структурирования спора, Decision Matrix, когда
> варианты стабилизируются, Red Teaming перед фиксацией решения.

Агент называет выбранную модель и причину выбора, применяет процедуру
карточки и возвращает артефакт с допущениями и триггером пересмотра.

## Структура репозитория

```
thinking-toolkit/
├── SKILL.md                  # вход: контракт, роутинг, воркфлоу
├── references/
│   ├── catalog.md            # индекс, алиасы, сигналы выбора, рецепты
│   └── <model>.md            # 30 операционных карточек, по одной на модель
├── agents/openai.yaml        # опциональные метаданные для хостов
├── scripts/validate_skill.py # детерминированная валидация структуры
├── tests/                    # регрессионные тесты валидатора
└── install.sh                # копирование payload в каталоги скиллов
```

### Разработка

```bash
python3 scripts/validate_skill.py .        # инварианты структуры и контента
python3 -m unittest discover -s tests -v   # регрессионные тесты валидатора
```

Валидатор охраняет инварианты, делающие скилл надёжным: каждая карточка
содержит все десять операционных секций, каждая ссылка разрешается внутрь
репозитория, payload скилла не содержит внешних URL (обязан работать полностью
офлайн), а каталог точно совпадает с набором карточек.

## Принципы дизайна

- **Провайдер-нейтральность по построению.** Ни вызовов инструментов, ни
  браузинга, ни исполнения кода, ни допущений о памяти. Достаточно любой
  способной LLM с доступом к файлам.
- **Минимально достаточный набор моделей.** Одна модель по умолчанию, максимум
  три, и явное разрешение не использовать ни одной: коммуникационная модель
  выбирается только после того, как анализ под ней состоятелен.
- **Сохранение агентности пользователя.** Результаты моделей помогают решить;
  решение остаётся за пользователем. Скилл не производит уверенность, которой
  нет в доказательствах.
- **Глубина по ставкам.** Быстрый проход для обратимых малозначимых решений;
  глубокий — с проверками чувствительности и поиском опровержений — для
  значимых или необратимых.
- **Детерминированные ворота качества.** Валидатор на чистой стандартной
  библиотеке держит все 30 карточек структурно полными, а таблицы роутинга —
  синхронными с набором карточек.
